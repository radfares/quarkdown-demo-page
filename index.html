This chapter dives into these core components, which form the foundation of any robust agent framework. The Conductor: The Runtime and Orchestration Engine At the very heart of any agent is its runtime, or orchestration engine. It is the most critical, yet often most invisible, component of an agent framework. If the LLM is the agent’s brain, providing reasoning and intelligence, the runtime is its central nervous system—the conductor that manages its lifecycle, state, and the continu- ous loop of perception, reasoning, and action. It is what transforms a static, single- shot script into a dynamic, stateful entity capable of autonomous, cyclical operation. To truly appreciate what a runtime does, it’s essential to first understand the pro- found challenges a developer would face without one.

The Developer’s Dilemma: Building an Agent from Scratch Imagine you have an LLM and a set of Python functions (tools). You decide to build an agent to solve a multi-step problem. Your first attempt might look like a simple script:

  1. Take user input.
  2. Call the LLM with the input and a list of tools.
  3. If the LLM asks to use a tool, execute that tool’s function.
  4. Take the tool’s output and feed it back to the LLM.
  5. Get the final answer and print it. This works for a single tool call. But what happens when the task requires multi- ple tool calls? Or when the agent needs to decide between two different tools based on the result of a third? Suddenly, your simple script explodes in complexi- ty. You would be forced to manually implement: The Execution Loop You’d need to write a while loop that continues until the agent decides it’s finished. How does it decide? You’d have to parse the LLM’s output for a “stop” signal, a fragile and error-prone process. State Management Where does the conversation history live? In a global variable? A complex object you pass around everywhere? How do you ensure the state is cor- rectly updated after each step without bugs? What if one tool needs the out- put from two previous, non-sequential tools? You are now responsible for managing a complex dependency graph in your code. Lifecycle Management What if a tool call takes 30 seconds? Your application freezes. What if you need a human to approve a step? You have no way to pause the execution, save its exact state (including which line of code it’s on), and resume it later. Error Handling What if a tool fails or an API times out? Your entire loop might crash. You’d have to build sophisticated try...except blocks around every single step and create a mechanism for the agent to recover and retry. Without a framework, a developer quickly ends up building a brittle, tangled web of if/else statements, while loops, and manual state tracking—a house of cards that is difficult to debug, impossible to scale, and a nightmare to maintain. This is the fundamental problem that an orchestration engine solves. It is the op- erating system for your agent. A robust runtime provides a set of powerful abstractions that handle the opera- tional complexity of running an agent, allowing the developer to focus on the agent’s logic. Let’s break down its core responsibilities. The Execution Loop (The “Perceive-Reason-Act” Cycle) The defining characteristic of an agent is its ability to operate in a cycle. The run- time is responsible for managing this fundamental loop: perceive new informa- tion, reason about the next action, and act on that decision. Asynchronous by Default: The Non-Blocking Engine Modern agentic systems are inherently I/O-bound. They spend most of their time waiting—for an LLM to generate tokens, for a tool to return data from an API, or for a database query to complete. A synchronous framework would freeze during these waits, leading to unresponsive applications and inefficient resource use. A production-grade runtime, therefore, must be asynchronous by default. It should be built on an async/await paradigm, ensuring that long-running opera- tions don’t block the entire system. This is the foundation that enables several oth- er critical features: Streaming An agent can stream back tokens or thoughts while simultaneously waiting for a tool to finish. Concurrency Multiple tools or even multiple sub-agents can be run in parallel.

Control Flow and Routing After an agent acts, what happens next? The runtime is responsible for routing the execution based on a set of rules. This control flow can be deterministic (hard- coded) or dynamic (LLM-driven). Deterministic Routing This provides reliability and predictability. A great example is CrewAI’s. By setting process=Process.hierarchical, the developer instructs the runtime to always route tasks through a manager agent, which then delegates to workers.

CrewAI Example: Defining a deterministic, hierarchical runtime process.

from crewai import Crew, Process crew = Crew( agents=[researcher, writer], tasks=[some_task], process=Process.hierarchical, # This is a directive to the runtime engine. manager_llm=“gpt-4o” # The manager will orchestrate the workers. ) Dynamic (LLM-Driven) Routing This provides flexibility. The LLM itself decides which agent should receive the task next. The runtime is responsible for interpreting this decision and routing control. Google’s ADK implements this via a special transfer_to_agent function call. When an agent’s LLM outputs this, the ADK runtime intercepts it and transfers execution to the named agent.

This abstracts away the complexity of managing threading or async IO.

The Agent’s Mind: Memory What separates a truly intelligent assistant from a mere command-line tool? The ability to remember. A simple calculator can answer 2+2 correctly every time, but it has no recollection of the previous calculation. A true assistant, however, can answer, “What was the result of that last calculation?” or “You know I prefer my reports in Celsius, right?”. This capacity for recall—this memory—is what enables coherence, personalization, and genuine utility. In an agent framework, memory is not a single, monolithic concept. It is a struc- tured system designed to provide the agent with the right context at the right time. As we have described in chapter 1, we can categorize agent memory into two distinct types based on its scope and persistence: Short-Term Memory (Session Context) The agent’s “working memory” for the current task. Long-Term Memory The agent’s persistent knowledge base that spans across multiple conversations. Let’s explore how a robust framework provides both. Short-Term Memory: The Conversational Workspace As we discussed in the Runtime and Orchestration Engine section, every agent in- teraction happens within a session that has a state. This session state is the agent’s short-term memory. Its primary purpose is to maintain coherence and context within a single, continuous task or conversation. It holds the chat history, the re-

sults of recent tool calls, and any other information directly relevant to the job at hand. To recap, a developer building an agent from scratch would face the Conversational Context Problem: manually managing the growing list of messages and state updates to prevent context window overflow and ensure the LLM has the necessary information for its next step. An agent framework’s runtime solves this by formalizing session state manage- ment. As we saw with LangGraph’s, the runtime isn’t just appending to a list; it’s managing a structured state object according to predefined rules (reducers), en- suring the conversational workspace is maintained automatically and reliably.

Long-Term Memory: The Persistent Knowledge Base Let’s say a user tells your agent, “My shipping address is 123 Main St.” In the next conversation, a week later, they ask, “Ship my order to my address.” Short-term memory, which is scoped to a single session, is of no help here. The agent needs to access a persistent, long-term knowledge store. This is the Persistent Knowledge Problem. Without a framework, a developer would have to design a database, write code to extract “facts” from conversations, save them, and then, most critically, figure out how to retrieve only the relevant facts for a new query. You have just stumbled into the incredibly difficult problem of information retrieval. Long-term memory is the agent’s persistent knowledge store. Its purpose is to en- able personalization and recall of information across different conversations and over time. Simply storing information is the easy part. The far more difficult challenge is re- trieval. You cannot simply dump a user’s entire interaction history into the LLM’s prompt. The core problem a long-term memory system solves is finding the few, most relevant pieces of information from a vast knowledge base and making them available to the agent for its current task. Modern frameworks almost always solve this with a Retrieval-Augmented Generation (RAG) architecture, often powered by a vector database. The flow is as follows:

  1. Ingest: Key information is extracted from a conversation and stored.
  2. Embed: The information is converted into a numerical representation (an em- bedding) that captures its semantic meaning.
  3. Store: The embedding and the original text are stored in a searchable index.
  4. Search: When the agent needs information, its query is also embedded, and the system searches for the most semantically similar pieces of stored information.

Page 9

Frameworks provide this complex RAG pipeline as a managed service. CrewAI, for instance, makes enabling long-term memory incredibly simple. By setting memory=True on the Crew, the framework automatically configures a persistent SQLite database for storing key-value memories and a ChromaDB vector store for semantic search.

CrewAI Example: Enabling a complete long-term memory system with one parameter.

from crewai import Crew, Process crew = Crew( agents=[researcher, writer], tasks=[research_task, analysis_task], process=Process.sequential, memory=True, # This flag activates the long-term memory system. verbose=True )

Under the hood, CrewAI now manages a persistent RAG pipeline for the agents.

Google’s ADK provides another excellent example with its VertexAiMemoryBankService. This illustrates the “tool-based” interaction with long-term memory. The agent doesn’t “magically” remember; it is given a load_memory tool. When it determines it needs past information, it acts by call- ing this tool with a specific query. The runtime, connected to the VertexAiMemoryBankService, executes the search and returns the results.

Use the ‘load_memory’ tool " “if the answer might be in past conversations.”, tools=[load_memory] # The agent is given the ability to query its memory. ) The Synergy of Memory The true power of an agent’s memory comes from the seamless interplay between its short-term and long-term systems. A typical cognitive loop looks like this:

  1. The agent receives a new user query. The runtime adds this to its short-term memory (the current session state).
  2. The agent analyzes the query and the immediate context from its short-term memory. It might realize it’s missing a key piece of information (e.g., “What is the user’s favorite topic?”).
  3. It then formulates a query and uses a tool to search its long-term memory.
  4. The long-term memory system retrieves the relevant fact (“The user’s favorite topic is AI ethics”).
  5. This retrieved fact is then loaded into the agent’s short-term memory as con- text for the current step.
  6. Finally, with both the immediate conversational context and the retrieved long-term knowledge now present in its working memory, the agent formu- lates its final, intelligent response. To provide accurate and personalized responses, an agent must balance immedi- ate context with persistent knowledge. The Agent’s Hands and Senses: The Tooling Interface An agent that can only talk is a conversationalist. An agent that can act is a collab- orator. The bridge between the agent’s reasoning mind and the vast world of digi- tal and physical actions is its tooling interface. This component is the standard- ized system that allows an agent to perceive and manipulate its environment be- yond the confines of the LLM. It is what enables an agent to browse the web, query a database, send an email, or even turn on a smart light. A well-designed tooling interface is a non-negotiable pillar of any serious agent framework. It provides the essential abstraction layer that makes external capa- bilities safely and reliably available to the agent’s reasoning engine. The Developer’s Dilemma: The Disconnected Agent Imagine you want to give your LLM-powered agent a new skill: the ability to check the current weather. Without a tooling interface, your path is fraught with complexity and risk: Parsing Intent First, you’d need to prompt the LLM to recognize a user’s request for weather and instruct it to output a specific, parsable string, like TOOL_CALL: get_weather(city=’San Francisco’) . This is fragile. A slight deviation in the LLM’s output format breaks your entire system. You are now in the business of writing complex regular expressions to parse model output. Executing the Function Once you’ve parsed the request, your code needs to map the string get_weather to your actual Python function, get_weather_forecast() . You’d have to build and maintain a registry of function names to function objects. Handling Arguments You then need to parse the arguments ‘San Francisco’ and pass them cor- rectly to your function. What if the LLM hallucinates an argument that your function doesn’t accept? Your code will crash unless you build robust validation. Security Risks What if your tool was a code executor that takes a string of Python code and runs exec() on it? If an adversary can trick your LLM into outputting TOOL_CALL: execute_python(code=’import os; os.system(“rm -rf /”)’) , you have a catastrophic security vulnerability. This manual, ad-hoc approach is unscalable, insecure, and brittle. A proper tool- ing interface solves these problems by providing a standardized, secure, and in- trospectable way to define and execute tools.

Core Responsibilities of a Tooling Interface A robust tooling interface handles the entire lifecycle of a tool call, providing three critical functions: definition, selection, and execution. Tool Definition and Registration This is the process of making a piece of code (like a Python function) available to the agent. A good framework provides a simple, declarative way to do this. The developer shouldn’t have to write complex boilerplate; they should be able to “register” a function as a tool with minimal effort. This is often achieved through decorators or wrapper classes. CrewAI’s is a classic example of this principle. By simply adding @tool above a function, the develop- er signals to the framework that this function is an agent capability.

CrewAI Example: A simple, declarative way to define a tool.

from crewai.tools import tool @tool(“Calculator Tool”) def calculator(expression: str) → str: "”“Useful for solving simple math expressions.””” return eval(expression) Under the hood, this decorator does something crucial: it performs introspection. It inspects the function’s name (calculator), its docstring (“Useful for solving...”), and its parameters and type hints ( expression: str ). It then uses this informa- tion to generate a formal schema (often a JSON Schema). Tool Selection (Function Calling) This schema, generated during the registration process shown in Figure 4-3, is the key to reliable tool use. Instead of asking the LLM to generate a fragile string, the framework passes the schemas of all available tools directly to the model as part of its prompt. Modern LLMs are trained to understand these schemas and can output a structured function call when they determine a tool is needed. Figure 4-3. The Tooling Interface. Frameworks use introspection to convert native code into the formal JSON schemas required for function calling. This is a monumental shift. The developer is no longer in the business of parsing unpredictable strings. The LLM’s output is a structured object that says, “I want to call the tool named calculator with the argument expression set to 2+2 .” This is reliable, safe, and built upon the model’s native capabilities. Secure Execution Once the agent’s runtime receives a valid function call request from the LLM, it is responsible for securely executing the corresponding code. The tooling interface ensures that: Only registered tools can be called. An LLM cannot simply invent a function to run. Arguments are validated against the schema. If the LLM provides an incorrect argument type, the framework can catch it.

Page 12

Execution is sandboxed where necessary. For high-risk tools like code inter- preters, the framework should provide a secure execution environment. Google’s ADK, for instance, provides a BuiltInCodeExecutor that is sandboxed to prevent malicious code from affecting the host system. By integrating these core responsibilities, the tooling interface provides the neces- sary “connective tissue” between an agent’s internal reasoning and its external environment. It replaces the fragile, manual workflows of the past with a robust protocol that ensures every interaction with an external system is predictable, validated, and safe. This transition from simple text generation to reliable, tool- augmented action is what truly marks the evolution from a conversational chat- bot to a functional, autonomous AI agent. The Team Players: Multi-Agent Communication As we push the boundaries of what AI can do, we quickly find that a single, mono- lithic agent—no matter how powerful—often falls short. Complex problems are rarely solved by one generalist; they are solved by a team of specialists, each bringing their unique expertise to the table. An AI system designed to write a market analysis report is far more effective if it’s composed of a Research Agent, a Data Analysis Agent, and a Writing Agent, rather than one “Business Agent” trying to do everything. This is the paradigm of multi-agent systems. But for a team to be effective, its members must be able to communicate. The multi-agent communication compo- nent of a framework provides the protocols and interfaces that enable this collab- oration. It is the system that allows agents to delegate tasks, share information, and work together as a cohesive unit. The Developer’s Dilemma: Orchestrating a Team Imagine you’ve built three specialized agents. How do you make them work to- gether? Without a framework, you become the manual project manager, facing a daunting orchestration challenge: Routing and Delegation How does the “main” agent decide which specialist to call? You’d have to write complex routing logic, perhaps parsing the main agent’s output for keywords like “research” or “write” to decide which sub-agent to invoke next. This is brittle and doesn’t scale. State and Context Passing How does the Writing Agent get the findings from the Research Agent? You would need to manually capture the output from one agent’s execution and format it correctly to be the input for the next. This creates tight, hard-cod- ed coupling between your agents, making the system rigid and difficult to modify. Control Flow What if the Writing Agent needs to ask the Research Agent for clarification? This requires a cyclical flow of control, which is notoriously difficult to manage in a simple script. You are now building a complex state machine from scratch. A multi-agent communication system solves this by providing a standardized way for agents to interact, manage control flow, and share context, turning a chaotic collection of individuals into an organized and effective team. Core Principles of Multi-Agent Communication A framework facilitates collaboration by providing clear mechanisms for delega- tion and information sharing. Explicit Routing In some systems, the control flow is deterministic. The developer defines the exact sequence of agent interactions. The output of one node (representing an agent’s turn) is an update to the shared state object. The next node in the graph receives this updated state as its input.

context=[research_task] ) The Agent’s Charter: Instructions and Prompting We have assembled the core machinery of an agent: a runtime to orchestrate its actions, a memory to provide context, tools to interact with the world, and proto- cols for collaboration. But what animates this machinery? What gives the agent its purpose, its personality, and its rules of engagement? This is the role of the Instructions and Prompting system. This component is the agent’s charter—its constitution. It is a structured system for defining and managing the agent’s core identity, goals, and operational bound- aries. It is the primary interface between the developer’s high-level intent and the LLM’s low-level reasoning. Without a robust prompting system, an agent is like a powerful engine without a steering wheel—capable of great force but with no direction. The Developer’s Dilemma: The Unpredictable Agent Imagine you’re building a customer support agent. You want it to be helpful, em- pathetic, and to never give financial advice. If your only tool is a single, massive string of text you send to the LLM, you face immediate challenges: Brittleness

Page 16

A simple change—like adding a new tool—requires you to manually edit a large, monolithic prompt, risking unintended side effects. You might acci- dentally remove a crucial safety instruction while adding a new capability. Lack of Structure How do you reliably inject dynamic information, like the user’s name or the conversation history? You resort to fragile string formatting (f”...”), which can easily break if the data contains unexpected characters or if the tem- plate becomes complex. Inconsistency How do you ensure that certain rules (like “never give financial advice”) are applied consistently across every single turn of the conversation? Manually including this in every prompt is repetitive and error-prone. No Separation of Concerns The agent’s core identity (its persona), its immediate task (the user’s latest query), and its available tools are all jumbled together. This makes the sys- tem difficult to reason about, debug, and maintain. A dedicated prompting system solves these problems by providing a structured, modular, and dynamic way to construct the final instructions sent to the LLM. Core Responsibilities of a Prompting System A modern agent framework treats prompting not as simple string creation, but as a formal system for composing context. Its key responsibilities are as follows. Modular and Composable Prompts Instead of a single block of text, a good framework allows prompts to be built from smaller, reusable components or “slices.” This separates different concerns, making the system vastly more maintainable. Google’s ADK, for example, formalizes this with the instruction parameter. This is the agent’s core directive, separate from the immediate user query or the tool def- initions. This separation ensures that the agent’s fundamental identity remains constant, while the specifics of the task can change with each turn.

ADK Example: Separating the agent’s core instruction from the task.

from google.adk.agents import LlmAgent

The ‘instruction’ is the agent’s permanent charter.

support_agent = LlmAgent( name=“SupportAgent”, model=“gemini-2.5-flash”, instruction=””” You are a helpful and empathetic customer support assistant. Your primary goal is to resolve user issues. You must NEVER give financial advice under any circumstances. "”” )

When the agent runs, the runtime combines this core instruction with the

current user message and available tools to form the final prompt.

runner.run(new_message=“My payment failed.”)

A well-defined persona can improve the quality and safety of the agent’s output. CrewAI formalizes this with its role, goal, and backstory parameters. These are not just descriptive metadata; they are core components that the CrewAI runtime weaves together to construct the final, comprehensive system prompt for the agent. This structured approach encourages developers to think deeply about the agent’s identity.

Tool Schema Integration As discussed in the Tooling Interface section, the prompting system is responsible for taking the schemas of the available tools and formatting them in a way the LLM can understand. It constructs the part of the prompt that says, “Here are the tools you have available, and here is how you must call them.” This integration is a critical function of the runtime and prompting system, ensuring that tool use is reliable and structured. Frameworks in Focus: Choosing Your Orchestration Engine Throughout this chapter, we’ve explored the five core components that define a modern agent framework. To bring these abstract concepts to life, let’s compare three powerful, cloud-agnostic frameworks: Google’s Agent Development Kit (ADK), LangGraph, and CrewAI. While all three can build sophisticated agents, they embody fundamentally different architectural philosophies. Understanding these differences will equip you to choose the right tool for your specific needs.

Understanding whether your use case requires a top-down hierar- chy, a rigid state-machine graph, or a modular component-based shell is the first step in selecting the right tool for the job. At their core, the choice comes down to your preferred development model and the level of abstraction you desire: CrewAI is a high-level, declarative framework for multi-agent collaboration. You define the “who” (agents with roles) and the “what” (tasks to be done). The framework handles the “how” by automatically orchestrating the workflow. Google ADK is a “batteries-included” SDK. It provides a comprehensive tool- kit of classes, services, and plugins, treating agent development like traditional object-oriented software engineering. You configure a pre-built agentic loop. LangGraph is a “control-flow-first” orchestration library. It models agent logic as an explicit state machine, giving you fine-grained control over every step and transition in your workflow. Let’s see how this philosophical difference plays out across the five core compo- nents of an agent framework. Runtime and Orchestration Engine CrewAI offers the most abstracted runtime experience. Developers define a Crew populated with specific agents and tasks, choosing either a sequential or hierar- chical process. From there, the framework’s underlying engine takes over, han- dling the entire execution flow and seamlessly passing information between agents without requiring manual step definition. In contrast, Google ADK relies on an implicit, model-directed loop. A developer in- stantiates an LlmAgent with instructions and tools, and the framework’s Runner manages the cyclical “perceive-reason-act” cycle behind the scenes. You configure the agent’s capabilities, but the runtime handles the looping logic. LangGraph takes a fundamentally different, explicit approach. It requires devel- opers to define the control flow themselves by adding execution nodes (functions) and routing edges (transitions) to a StateGraph . This makes complex routing, cycles, and branching first-class citizens of the architecture, directly visible in the application code. Memory Systems When it comes to managing context, CrewAI heavily abstracts memory manage- ment. Short-term memory is naturally handled as context is passed between tasks, while persistent, long-term memory can be enabled with a simple memory=True flag, which instantly spins up a built-in RAG pipeline for persis- tence and retrieval.

Page 19

Google ADK treats memory more like a pluggable piece of infrastructure. Developers provide a SessionService for short-term conversational context and a MemoryService for long-term knowledge retention. Within ADK, an agent typically interacts with its long-term memory by explicitly calling a dedicated load_memory tool. LangGraph, leaning into its explicit design, integrates memory directly into its stateful graph architecture. Short-term memory is stored in the graph’s State object and saved by a Checkpointer , while long-term knowledge is accessed via a Store that developers can programmatically query from any node. The Tooling Interface Equipping agents with external capabilities also varies by framework. CrewAI and Google ADK both favor direct tool registration. In CrewAI, developers simply define tools as Python functions—often tagged with an @tool decorator—and as- sign them to an agent. Similarly, Google ADK allows developers to pass native Python functions directly into an agent’s tools list. Both frameworks automatically handle the heavy lifting of code introspection, schema generation, and secure execution. LangGraph approaches tooling through node-based execution. Rather than at- taching tools directly to an agent object, tools are typically housed within a dedi- cated ToolNode in the graph. When the agent’s reasoning node determines a tool call is necessary, the graph’s edges explicitly route the execution state to the ToolNode to perform the action. Multi-Agent Communication The approach to coordinating multiple agents highlights the core philosophies of each framework. CrewAI was designed specifically with multi-agent systems in mind. Communication is a core primitive determined by how tasks are structured and assigned within a crew, with the framework’s overarching process automati- cally orchestrating interactions. Google ADK promotes a more hierarchical communication model. Sub-agents are treated as callable tools ( AgentTool ) that are given to a parent agent, creating a natural delegation structure in which a manager assigns work to a specialist. LangGraph, unbound by strict hierarchies, enables entirely flexible topologies. Because agents are simply nodes within a graph, communication pathways are defined entirely by the edges connecting them. This allows developers to build any pattern imaginable—from a central supervisor or a collaborative swarm to fully custom workflows that mirror CrewAI’s structured processes while retaining explicit developer control. Instructions and Prompting Finally, the way developers dictate the agent’s persona and logic differs signifi- cantly. CrewAI relies on structured persona definitions, requiring developers to define an agent by its role, goal, and backstory. The framework then seamlessly combines these elements into a comprehensive prompt for the underlying LLM, abstracting away the nuances of prompt engineering. Google ADK utilizes structured parameters on the Agent class itself, such as an instruction parameter that features built-in support for dynamically injecting state variables (like {topic} ) directly into the prompt. LangGraph, true to form, is entirely programmatic. Prompts are typically con- structed dynamically inside individual nodes, granting the developer absolute control to craft, format, and inject prompts using bespoke logic based on the exact current state of the graph.

Page 20

Choosing the Right Framework Ultimately, the choice of framework comes down to the specific needs of the project and the developer’s preferred level of abstraction. CrewAI is the ideal choice for the rapid development of multi-agent systems where the collaboration pattern is well-defined (such as sequential or hierarchical pipelines) and a high- level, declarative API is preferred. Google ADK offers a highly component-based development experience akin to building a traditional software application, making it excellent for rapid prototyp- ing, especially when the agent’s logic is primarily directed by the model. Conversely, LangGraph is the definitive choice when a project requires explicit, fine-grained control over complex, stateful workflows. It truly shines when build- ing systems that involve intricate cycles, human-in-the-loop approvals, or novel multi-agent topologies that outgrow standard hierarchical patterns. Conclusion The five core components—Runtime, Memory, Tooling, Communication, and Prompting—are the essential building blocks of all capable AI agents. Together, they elevate a standard language model into a dynamic, autonomous system. Without a robust runtime, an application is just a static script, unable to manage its own execution loops or state. Without memory, the system has no context, ren- dering it unable to personalize interactions or recall past events. Without a tool- ing interface, the model is restricted to generating text, completely unable to trig- ger real-world actions or retrieve live data. Without communication protocols, it cannot coordinate with other specialized agents to divide and solve complex problems. And finally, without a structured prompting system, the agent lacks the clear instructions and functional boundaries required to reliably accomplish its intended tasks. The ultimate job of a framework is to act as the final assembly line. On every turn of an agent’s execution loop, it gathers all the necessary components: the core in- structions, the relevant long-term and short-term memories, the available tools, and the latest user message. It then intelligently assembles these pieces into a sin- gle, coherent prompt that is sent to the LLM. This process, repeated on every turn, is what allows a structured, modularly defined agent to engage in dynamic, con- text-aware reasoning. It is the mechanism that translates the developer’s high-lev- el architectural decisions into low-level, actionable instructions for the model, en- suring that the agent acts with purpose, within its boundaries, and with all the in- formation it needs to succeed. With a solid understanding of these foundational components, we are now ready to move from theory to practice. In the next chapter, we will use Google’s Agent Development Kit (ADK) to explore the hands-on design and construction of indi- vidual agents, detailing how to craft effective instructions, build robust custom tools, and orchestrate both LLM-directed and workflow-driven behaviors.
